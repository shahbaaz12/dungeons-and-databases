Lesson 06 · Boundaries within

Divide one table without leaving one machine.

Partitioning keeps one logical table for the application while PostgreSQL stores separate physical pieces beneath it. The boundaries help only when the query and the data lifecycle follow them.

Partition keysPruningRetentionOne-machine ceiling

The Dragon’s Counsel

“A wall helps only when the traveler knows which gate to enter.”

The partition key must match the questions and lifecycle of the data.

01 · What the split means

One table above. Many physical tables below.

To the application, orders remains one table. Underneath, PostgreSQL can place August orders in one partition, September orders in another, and so on. Inserts are routed to the matching child. Queries still name the parent.

→

Junolder
Julrecent
Augcurrent

Every piece still lives in the same PostgreSQL instance. They share the machine’s CPU, buffer pool, WAL, storage bandwidth, and fsync path. This is organization inside one castle, not a new castle.

02 · The reward

A matching filter lets PostgreSQL ignore whole regions.

Suppose five years of monthly partitions give us sixty physical pieces. A query asks for the last seven days and includes created_at, our partition key. PostgreSQL can prove that fifty-nine pieces cannot contain the answer and plan only the current month. This is partition pruning. 

SELECT *
FROM orders
WHERE created_at >= now() - interval '7 days';
MayprunedJunprunedJulprunedAugopened

Remove the time filter and PostgreSQL cannot know which partition to skip. It must consider all sixty, often scan all sixty, and combine the results. More partitions then mean more planning work and more indexes to inspect. A partition helps only a query shaped around its key.

03 · The key

Choose the boundary the data already follows.

Common partition strategies
StrategyNatural fitWeakness
RangeTime-series data, prices, ordered identifiersThe newest range often receives all current writes.
ListA small known set such as regions or statusesNew values need a destination and uneven groups stay uneven.
HashEvenly spread rows when range pruning is unimportantRange queries cannot discard neighboring buckets.

The key is a long-lived design choice. Queries must include it to prune, rows belong to a partition because of it, and changing it later means moving data. PostgreSQL also requires every column of the partition key to appear in a primary key or unique constraint declared on the partitioned table, because separate partitions cannot otherwise enforce uniqueness across one another. 

CREATE TABLE orders (
  id bigserial,
  customer_id bigint NOT NULL,
  created_at timestamptz NOT NULL,
  total numeric,
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_08 PARTITION OF orders
FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

The definition and key rules follow PostgreSQL’s official Table Partitioning documentation.

04 · The clean exit

Retention becomes a boundary operation.

Deleting a year of old orders row by row creates a year of work: each row is located, changed, logged in WAL, and left as dead space until vacuum can reclaim it. Index entries must be cleaned too.

If that year occupies whole time partitions, retention can detach the old piece and drop it. The database changes the table’s structure instead of visiting every row inside it.

Row deletionVisit every old row

Large WAL volume, dead tuples, index cleanup, and vacuum work follow the deletion.

Partition retirementRemove one boundary

Detach for archive or inspection, then drop the old physical table.

ALTER TABLE orders DETACH PARTITION orders_2021_03;
DROP TABLE orders_2021_03;

The same boundaries make maintenance smaller. PostgreSQL can VACUUM, ANALYZE, or REINDEX one partition at a time instead of treating years of data as one maintenance unit.

05 · The multiplied furniture

Every partition brings its own indexes and planning work.

A partitioned index is implemented as matching indexes on the child partitions. Sixty monthly tables with three indexes mean many smaller structures to create, inspect, and maintain. That can be useful—the hot index is smaller—but hundreds or thousands of pieces can make planning and schema changes expensive.

Partition size should follow useful operations, not an arbitrary urge to make pieces. A boundary is good when it matches query pruning, retention, loading, or maintenance. “One partition per customer” may create tens of thousands of tables without helping the actual query path.

  • Verify common queries include the partition key.
  • Keep the number and size of partitions operationally manageable.
  • Create future partitions before data reaches their boundaries.
  • Measure pruning with EXPLAIN; do not assume it happened.

06 · The unchanged ceiling

Partitioning does not add another machine.

Partitions can shrink the pages a query considers and turn retention into a cheap structural action. They do not give PostgreSQL another CPU, another WAL stream, another fsync path, or another storage device. A write-heavy system can still exhaust the same machine after the table is beautifully divided.

Yet partitioning is excellent preparation for sharding. The team has already chosen a routing key, handled data movement, lived with queries that omit the key, and learned that cross-boundary operations cost more. The next split keeps those lessons but places the pieces on different machines.

Where we stand

The table now has useful physical boundaries. Queries and retention can skip work, while the machine’s resource ceiling remains unchanged.
