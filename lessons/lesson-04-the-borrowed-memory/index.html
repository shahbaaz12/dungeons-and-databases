Lesson 04 Answers remembered

Lesson 04 · Answers remembered

Keep the answer close—but know when it lies.

An index helps the database find an answer with fewer page reads. A cache can avoid the database query entirely. That buys headroom, but it also moves freshness and failure into the application.

Cache-asideInvalidationStampedesCold starts

The Dragon’s Counsel

“A remembered answer is swift. An old answer is still wrong.”

A cache is useful only when we can name what it saves and how stale it may become.

01 · Another memory

An external cache is a second buffer pool.

PostgreSQL already keeps recently used pages in its buffer pool. An external cache, such as Redis, keeps complete answers chosen by the application: a product record, a customer dashboard, or the result of an expensive aggregation.

That distinction matters. A database buffer hit avoids storage, but PostgreSQL must still parse the query, find pages, apply filters, join rows, and build the result. An application-cache hit can skip both the storage trip and most of that database CPU work.

Database bufferRemembers pages

Managed by the database. Every query still enters PostgreSQL and does query work.

External cacheRemembers answers

Managed by the application. A hit can return without asking PostgreSQL at all.

But the second memory does not know when the first one changes. The moment we cache an answer, the application becomes responsible for keeping that answer acceptably fresh.

02 · The read path

Look in the cache first. Ask the database only on a miss.

The common pattern is called cache-aside. The application, not the cache, decides how a read should travel.

Cache-aside read
Applicationasks for customer 42
→
Cachelook for customer:42
→
Databaseonly when missing

Hit: return the cached answer. Miss: read from PostgreSQL, store the answer with an expiry, then return it.

This is valuable only when requests repeat. Ten thousand people requesting the same product can share one cached answer. Ten thousand people requesting ten thousand unrelated records produce ten thousand misses and still reach the database.

The cache hit rate is not the goal. The goal is a lower database query rate. A beautiful 99% number can hide the fact that the remaining 1% still overwhelms PostgreSQL.

03 · The write path

Write the truth, then forget the copy.

Suppose customer:42 is cached and the customer changes their address. Updating only PostgreSQL leaves the old address in the cache. Updating both sounds tidy, but two separate systems cannot be changed in one simple atomic step: either update can fail while the other succeeds.

The safer default is: commit the database write, then delete the cache key. The next reader misses, fetches the new truth from PostgreSQL, and repopulates the cache. We invalidate the copy instead of trying to maintain two truths.

Write then invalidate
Write PostgreSQLthe source of truth
→
Commit succeedsthe change is durable
→
Delete cache keynext read refills it

A small race can still exist: another reader may refill the old value between the commit and the deletion, or invalidation may fail. Expiry times, retries, versioned keys, or change streams can reduce that window. They do not remove the central decision: how long may this answer be stale?

04 · Fresh enough

A time-to-live is a product promise.

A cache entry usually expires after a time-to-live, or TTL. A five-minute TTL says more than “free this memory later.” It says the application may show information that is up to five minutes old if invalidation fails or no invalidation exists.

Freshness should follow the operation
AnswerPossible policyReason
Public product descriptionMinutes of TTLA brief delay is usually harmless.
Inventory available to sellShort TTL plus validationStaleness can oversell stock.
Account balance before paymentRead the authorityCorrectness matters more than avoiding one query.

There is no universal TTL. “Fresh enough” belongs to the business action. A product page, an account balance, and a fraud decision should not inherit the same consistency merely because they share Redis.

05 · The empty shelf

Popular misses arrive as a crowd.

Imagine one popular key receiving 20,000 reads per second. Its TTL ends. All 20,000 requests miss at nearly the same moment, and all try to rebuild the same answer from PostgreSQL. This is a cache stampede: the item is hottest precisely when its protection disappears.

Single-flight allows one request to rebuild the value while the others wait or use a slightly stale copy. Early refresh and background refresh spread the work before the hard expiry.

One expired keyWithout protection

Every miss reaches PostgreSQL and repeats the same expensive query.

One builderWith single-flight

One request refreshes the answer; the rest wait or temporarily use the old value.

A cold start is the same danger at system scale. After a restart or full cache flush, the hit rate is zero. If the database survives only while the cache is warm, the cache has become a hidden single point of overload. Provision and test PostgreSQL for that recovery path.

A 99.9% hit rate can tempt a team to size the database for the remaining 0.1%. The better the cache becomes, the more violent a total miss can be.

06 · Earn the cache

Do not add another memory when PostgreSQL already remembers.

If the active pages already fit comfortably in the database buffer pool and the query is inexpensive, an external cache may be slower than a local RAM hit: it adds a network hop, serialization, another service to operate, and invalidation bugs. Caching is justified when it removes repeated, measurable database work—not merely because the application reads often.

  • Measure the database query rate and CPU saved by cache hits.
  • Choose keys that repeat enough to be useful.
  • State the acceptable staleness for every cached answer.
  • Test stampedes, cache loss, and recovery at a 0% hit rate.
The Old Dragon“Borrow memory only after naming the truth it may forget.”

The Dragon’s Reckoning

Where we stand

The database can now avoid repeated reads, but every cached answer carries a freshness contract and a failure path.

What we learnedA cache remembers answers

Unlike the database buffer pool, a hit can skip database I/O and query CPU together.

What we solvedRepeated expensive reads

Cache-aside sends misses to PostgreSQL and lets later requests reuse the result.

What remainsOne database serves every write

Caching removes read work. It does not create a second durable authority.

Our system nowDatabase · cache · invalidation

We bought read headroom and accepted staleness, stampede, and cold-start responsibilities.
