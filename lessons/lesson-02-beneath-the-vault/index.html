Lesson 02 · Inside the machine

A row is never fetched alone.

The query asks for one order. Storage returns an entire page. Whether that page is already in memory decides whether the request feels instant—or waits at the vault door.

The Dragon’s Counsel

“Do not count rows yet. Count the doors the database must open.”

Pages are the unit of the journey. Rows are merely passengers.

The smallest useful door

Storage moves blocks, not individual rows.

PostgreSQL normally divides every table and index into 8 KB pages. Ask for a 100-byte row and the database still brings its whole page into memory. The expensive part is reaching storage; nearby rows arrive almost free.

The invisible boundary

Your working set is whatever traffic keeps touching.

It is not the table size and it is not a database setting. It emerges from the access pattern. A terabyte table can be fast when only recent pages are hot; a smaller table can thrash when requests jump randomly across all of it.

Pages fit

8 hot pages · 12 frames

Pages are revisited before the clock can evict them. After warm-up, almost every access is a hit.

Stable side of the cliff

Pages do not fit

24 hot pages · 12 frames

Every requested page displaces another useful page. Disk reads create more evictions, not relief.

Thrashing side of the cliff

The Dragon Explains

“The database never names your working set. It merely remembers what you touched.”

PostgreSQL’s clock sweep uses a small usage counter, capped at five. A hit raises the counter. When memory is full, the clock hand walks the frames: counters above zero fall by one; the first frame already at zero can be reused. Hot pages survive because traffic keeps refreshing them.

Clock-sweep eviction

A tiny local rule creates global memory.

There is no grand model of your traffic. Each frame knows only its page and a usage counter.

  1. 1Look for the page

    If its page number is already mapped to a frame, the access is a hit.

  2. 2Raise its memory

    A hit increases that frame’s usage counter, up to PostgreSQL’s cap of five.

  3. 3Sweep when full

    On a miss, the clock hand lowers positive counters as it searches for zero.

  4. 4Reuse the victim

    The zero-counter frame is replaced; a dirty victim must be written first.

The Dragon’s Reckoning

Where we stand

We can now explain why the same SQL swings between fast and slow without changing a single row: the pages were either already in memory or had to cross the disk boundary.
