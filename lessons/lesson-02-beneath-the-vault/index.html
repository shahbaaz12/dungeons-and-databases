Lesson 02 Inside the machine

Lesson 02 · Beneath the Vault

The database serves data from RAM.

Storage preserves the kingdom. Memory answers its questions. To understand why a query is fast one moment and slow the next, we must follow a single page between the two.

The Old Dragon “The row may sleep on disk, young keeper. It must wake in memory before it can speak.”

01 · The rule

The database reads from RAM, not directly from storage.

Your data rests in files on an SSD or another storage device. But PostgreSQL does not inspect a row while it is still sitting there. First, the part of the file containing that row must be in RAM. Only then can PostgreSQL read it and answer the query.

PostgreSQL therefore reserves an area of RAM called the buffer pool. Think of it as a temporary holding area for pieces of the database that are being used. A piece already in the buffer can be read immediately. A missing piece must first be copied from storage into the buffer, and is then read from there.

So both paths end in the same place: the data is read from RAM. The difference is whether the needed piece was already waiting there or had to make the trip from storage first.

02 · Why the rule matters

Why does reading from RAM make such a difference?

Imagine that you are reading a book. RAM is the open book on your desk: the page is already in front of you. An SSD is the library downstairs: you must leave the desk, find the book, and bring it back. Network storage is a library in another building: the request must travel even farther before the book reaches your desk.

In every case, you finally read at the desk. What changes is the time spent fetching the book. Computers work the same way, only much faster:

If one RAM read were stretched to one second, the comparable SSD trip would take about 17 minutes, and a network-storage trip about 2 hours and 47 minutes. These are teaching numbers, not a benchmark. Their purpose is to show why avoiding the trip matters so much.

03 · The page buffer

The buffer keeps useful parts of the database close.

PostgreSQL does not move one row at a time. It groups rows into fixed-size pieces called pages. A PostgreSQL page is normally 8 KiB. When one row is needed, the whole page containing that row is brought into RAM.

The buffer pool is divided into 8 KiB slots. Each slot holds one page. For example, if order 821 lives on page 17, PostgreSQL checks whether page 17 is already in one of those slots. Once page 17 is loaded, order 821—and every other row on that page—is available in RAM.

PostgreSQL also remembers which page is in each slot. The next request for anything on page 17 can reuse the same copy instead of visiting storage again.

Take a buffer configured as 1 GiB—often casually called “1 GB.” Because the binary unit divides evenly into 8 KiB pages, the number of slots is exact:

Example buffer pool1 GiB

1,073,741,824 bytes ÷ 8,192 bytes per page

8 KiB page slots131,072

If each page held roughly 80 rows of about 100 bytes, those slots could contain about 10.5 million rows at once. This is only a rough example: real pages also use space for page information, and real rows do not all have the same size.

04 · One request, two paths

If the page is missing, the database goes to fetch it.

Suppose the row we want lives on page 17. PostgreSQL first looks for page 17 in the buffer. What happens next depends on whether the page is already there.

Page found · no trip

Page 17 is already in the buffer.

  1. PostgreSQL finds the slot holding page 17.
  2. It reads the requested row from that page in RAM.
  3. The answer is returned.

This is called a buffer hit.

Page missing · storage trip

Page 17 is not in the buffer.

  1. PostgreSQL asks storage for the whole of page 17.
  2. The page travels from storage into a slot in the buffer.
  3. PostgreSQL reads the requested row from that page in RAM.
  4. The answer is returned.

This is called a buffer miss. The trip is the expensive part.

But what if every buffer slot is already occupied when a missing page needs to enter? PostgreSQL must choose an older page to remove. That is where the working set and eviction enter the story.

05 · Working set and eviction

Hot pages stay. Cold pages make room.

The working set is simply the group of pages the current queries keep asking for. If a dashboard repeatedly reads pages 3, 8, and 17, those pages are its working set. Because they are requested often, we call them hot pages.

When the buffer is full and a missing page must enter, PostgreSQL needs to reuse one slot. It uses a rule called the clock sweep. Imagine a hand moving around the buffer slots like the hand of a clock. Each slot has a recent-use score from 0 to 5. Reading a page again raises its score.

As the clock hand moves, a page with a score above zero gets another chance: its score drops by one, and the hand moves on. A page already at zero has not been used recently enough to earn another chance, so it can be removed and its slot reused. Repeated requests keep hot pages alive; pages that are no longer requested slowly become cold and are eventually removed.

One miss, followed step by step

Page 29 is requested, but it is absent. The clock hand begins at slot 1.

SlotPageRecent-use scoreWhat the hand does

Slot 3 now holds page 29 with a score of 1. The next search begins at slot 4.

Pages 3 and 17 survived this sweep because recent reads gave them another chance. Page 5 had a score of zero, so its slot was used for the incoming page 29. PostgreSQL does not need a perfect prediction of the future; repeated traffic naturally keeps the most useful pages warm.

When the active pages fit in the buffer, the first requests warm the cache and later requests are mostly hits. When the active pages are larger than the buffer—and traffic jumps around—useful pages can be evicted before they are requested again. Misses create more misses. That is thrashing.
