Lesson 02 Inside the machine

Lesson 02 · Inside the machine

A row is never fetched alone.

The query asks for one order. Storage returns an entire page. Whether that page is already in memory decides whether the request feels instant—or waits at the vault door.

8 KB pagesBuffer poolWorking setClock sweep

The Dragon’s Counsel

“Do not count rows yet. Count the doors the database must open.”

Pages are the unit of the journey. Rows are merely passengers.

First: what is a page?

Follow one requested row from query to memory.

A table looks like rows to us, but on disk it is a file divided into fixed-size blocks. PostgreSQL normally uses 8 KB pages for both tables and indexes.

1 · The question The query asks for one row 
SELECT * FROM orders
WHERE order_id = 821;

The database uses an access path to discover that order 821 lives on page 17.

2 · On disk Storage returns the whole page
1617≈80 rows18

Storage is not asked for “order 821.” It is asked for the 8 KB block called page 17.

3 · In memory The page enters a buffer frame
Buffer frame 6Page 17RAM

The buffer pool keeps this RAM copy so later requests may avoid another disk read.

4 · The answer PostgreSQL returns the requested row
order_id821statusshipped

The neighbouring rows arrived in memory too, even though this query did not ask for them.

One row may requireone full-page read

If page 17 is absent from memory, all 8 KB must cross the storage boundary.

Nearby rows may costno additional read

Once the page is in RAM, every row stored inside it is already available.

Therefore performance becomespages touched × page cost

The next question is not merely how many rows exist, but how many pages the access path visits.

About “≈80 rows”: it is a teaching estimate for rows around 100 bytes. Real capacity varies because pages contain headers and pointers, and rows have different sizes.

Next: the buffer pool

Every page request takes one of two paths.

Why use 1 versus 1,000?

It is a relative teaching model, not a benchmark. RAM access is dramatically cheaper than fetching a page from storage. Real latency also includes the operating-system cache, device, queue depth, and database work around the read.

Then: the working set

Traffic decides which pages are “hot.”

The working set is the collection of pages being revisited by current traffic. It is not the table size, and PostgreSQL does not calculate or configure it as a named object.

Performance changes sharply when the hot pages stop fitting. Each miss loads a page and evicts another page that may soon be needed. That self-reinforcing cycle is thrashing.

The Dragon Explains

“A vast vault can be fast when its visitors crowd one room.”

A 1 TB table whose traffic touches only the newest 8 GB may remain comfortable. A 50 GB table receiving random reads across all 50 GB may thrash on a 16 GB machine. Total data size alone does not reveal the active memory pressure.

Finally: clock-sweep eviction

How PostgreSQL chooses a page to evict.

Each buffer frame has a usage counter from 0 to 5. A hit raises it. When a miss needs space, a clock hand searches circularly for a frame whose counter is already zero.

Why hot pages survive

Traffic keeps raising their counters before repeated sweeps can reduce them to zero.

Why cold pages disappear

Pages no longer referenced gradually decay to zero and become inexpensive victims.

Why dirty pages cost more

A clean victim can be overwritten. A modified page must be written out before its frame is reused.

This is a deliberately small worked example of PostgreSQL’s normal shared-buffer replacement rule. PostgreSQL also uses specialised buffer-access strategies for some large operations so a sequential scan does not necessarily flood the entire shared pool.

The Dragon’s Reckoning

Where we stand

We can now explain why the same SQL swings between fast and slow without changing a single row: the pages were either already in memory or had to cross the storage boundary.

What we learnedPages are the currency

Rows, tables, and indexes all become page accesses before hardware can serve them.

What we solvedThe mysterious latency swing

Buffer hits are cheap; misses load pages and may evict something useful.
