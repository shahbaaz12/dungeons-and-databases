Lesson 02 Inside the machine

Lesson 02 · Beneath the Vault

The database serves data from RAM.

Storage preserves the kingdom. Memory answers its questions. To understand why a query is fast one moment and slow the next, we must follow a single page between the two.

The Old Dragon “The row may sleep on disk, young keeper. It must wake in memory before it can speak.”

01 · The rule

A read finishes in RAM—always.

The CPU cannot evaluate a row while that row is merely bytes in a database file. PostgreSQL’s query executor works with a page that is resident in memory. It checks values, follows row pointers, and returns the result from that in-memory page.

So “reading from disk” is shorthand for an extra journey: fetch the required page from the storage stack, place it into RAM, and only then read the row. A fast request skips that journey because the page is already waiting in memory.

A useful precision: the operating system may already have the file block in its own cache, so a PostgreSQL buffer miss does not guarantee a physical device read. The database still needs the page in RAM before the executor can use it.

02 · Why memory matters

RAM and storage live on different clocks.

The exact numbers change with hardware and workload. The important fact is the size of the gap: a local SSD page fetch is commonly orders of magnitude slower than a memory access.

SourceApproximate latencyRelative wait
RAM~100 nanoseconds1×

At those simplified rates, 1,000 memory accesses account for about 0.1 ms of raw access time. One thousand SSD reads account for about 100 ms. Database work, operating-system caching, queues, and parallelism change a real measurement—but they do not make the storage boundary disappear.

03 · The page buffer

The buffer pool is a shelf of page-sized spaces in RAM.

PostgreSQL normally divides table and index files into 8 KiB pages. Its shared buffer pool is memory divided into frames of that same size. Each frame can hold one page, and a small lookup structure records which (file, page number) currently occupies it.

This is why asking for one 100-byte row can still move an 8 KiB page. Storage and the buffer pool exchange pages; the executor finds the particular row after the page is in memory.

Take a buffer configured as 1 GiB—often casually called “1 GB.” Because the binary unit divides evenly into 8 KiB pages, its frame count is exact:

Example buffer pool1 GiB

1,073,741,824 bytes ÷ 8,192 bytes per page

Maximum page frames131,072

If each page held roughly 80 rows of about 100 bytes, those frames could contain about 10.5 million rows at once. That is a teaching estimate, not a capacity promise: page headers, row overhead, variable row sizes, table pages, and index pages all consume space.

04 · One request, two paths

A requested page either hits or misses.

Suppose PostgreSQL determines that the row it needs is on page 17 of orders.dat. The buffer manager looks for that exact page. From there, only one of two things can happen.

Buffer hit · fast path

Page 17 is already in RAM.

  1. The page map points to its buffer frame.
  2. PostgreSQL raises that frame’s usage counter.
  3. The executor reads the row from the frame and returns it.

No database-file read is needed.

Buffer miss · slow path

Page 17 is absent from RAM.

  1. The buffer manager chooses a frame to reuse.
  2. If its old page is dirty, PostgreSQL arranges for it to be written out.
  3. Page 17 is loaded from the storage stack into that frame.
  4. The page map is updated; then the executor reads the row from RAM.

The result is still served from RAM—after paying the load cost.

05 · Working set and eviction

Repeated traffic teaches the buffer pool what to keep.

The working set is the collection of pages current traffic keeps requesting. It is not a configured list. Pages become “hot” because they are hit repeatedly; pages become cold when requests stop returning to them.

PostgreSQL’s normal shared-buffer replacement rule is a clock sweep. Each frame has a small usage counter, capped at five. A hit raises the counter. When a miss needs room, a circular clock hand inspects frames: a positive counter is reduced and spared for now; a frame already at zero can be reused.

One miss, followed step by step

Page 29 is requested, but it is absent. The clock hand begins at frame 1.

FramePage beforeUsage beforeWhat the hand does

Frame 3 now holds page 29 with usage 1. The next search begins at frame 4.

Notice what emerges. Pages 3 and 17 survived this sweep because recent hits gave them another chance. If traffic hits them again, their counters rise again. A page that is no longer requested eventually decays to zero and becomes a victim. A dirty victim costs more because its changes must be preserved before the frame is reused.

When the active pages fit in the buffer, the first requests warm the cache and later requests are mostly hits. When the active pages are larger than the buffer—and traffic jumps around—useful pages can be evicted before they are requested again. Misses create more misses. That is thrashing.
