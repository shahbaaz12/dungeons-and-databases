Lesson 05 · Copy for reads

One truth. More places to read it.

A cache serves selected answers. Replication copies the database itself. Readers gain more machines, while writers gain a new question: when is a change truly safe and visible everywhere?

WALReplica lagRead your writesFailover

The Dragon’s Counsel

“Copies widen the reading hall. They do not multiply the quill.”

Replication buys read capacity by accepting coordination between copies.

01 · The copy

A primary writes. Replicas replay.

In the common arrangement, one primary accepts changes. One or more replicas receive those changes and apply them to their own copy. The application continues sending writes to the primary but can spread suitable reads across the replicas.

ReadsReplica AOwn CPU · RAM · storage

Each replica owns another CPU, another buffer pool, and another storage device. That is real read capacity. But all copies still contain the full data set, and every write still begins at one primary. Replication converts a capacity problem into a consistency problem.

02 · How the copy moves

Replicas follow the write-ahead log.

PostgreSQL records each change in the write-ahead log, or WAL, before altered table pages reach durable storage. Replication ships that ordered change stream to another server. The replica replays it against its own copy, rebuilding the same database state.

Physical replication sends storage-level changes and creates a close copy of the whole cluster. Logical replication describes row-level changes for selected tables, which allows a more selective or transformed subscriber. Both still have a sender, transport time, and a receiver that must apply work.

03 · When may we answer?

The acknowledgement decides speed versus safety.

The application sees a successful write when PostgreSQL sends an acknowledgement. The question is whether the primary may acknowledge after making the WAL durable on itself, or whether it must wait for a replica too.

AsynchronousPrimary answers first

Writes stay fast and survive replica trouble, but a primary failure may lose commits the replica had not received.

SynchronousWait for a replica

A promoted replica has acknowledged commits, but network or replica trouble can stall application writes.

Synchronous replication can use a quorum such as ANY 1: wait for any one member of a named replica set rather than one specific machine. It gives flexibility, not free certainty. Every acknowledgement rule chooses a point among write latency, durability, and availability.

04 · The distance behind

Replica lag is a queue, not a mysterious delay.

The primary produces WAL. The replica receives and replays it. If the primary produces changes faster than the replica can apply them, unapplied WAL accumulates. Lag is the depth of that queue, measured in bytes, log positions, or time.

Already replayedWaiting to replay

Slow replica storage, heavy reads competing for resources, network interruption, or a burst of writes can all deepen the queue. Replay must preserve dependency order; adding read replicas does not make the primary’s write stream disappear.

05 · The visible bug

“I saved it, then it vanished.”

A customer changes their address. The write commits on the primary. The next page load is routed to a replica that has not replayed that change, so the old address appears. The data was not lost; the application violated the user’s expectation to read their own writes.

Three ways to preserve read-your-writes
TechniqueHow it worksTradeoff
Sticky primaryAfter a write, keep that user’s reads on the primary for a short window.Simple, but shifts more read load to the primary.
Log-position trackingRecord the commit LSN and use only a replica that has replayed at least that far.Precise, but routing becomes smarter.
Entity routingRead recently changed entities from the primary; send unrelated reads to replicas.Targeted, but the application tracks affected data.

Not every read needs the same rule. A public feed can tolerate brief lag; a confirmation screen usually cannot. Route by the consistency the operation requires, not by a blanket “all reads go to replicas.”

06 · What copies cannot buy

Read capacity rises. The write ceiling remains.

Replicas do not meaningfully increase write throughput: the primary still orders the writes, generates WAL, and changes its pages. Replicas also do not shrink the working set, because each carries the full database. They are copies for reads and recovery, not pieces of a divided data set.

Failover is not merely “point traffic at the other server.” The system must prove the primary is dead, promote exactly one replacement, and prevent the old primary from accepting writes when it returns. Without fencing or a consensus-backed authority, two primaries can diverge—a split brain.

  • Decide how much acknowledged data may be lost.
  • Measure replay lag under both write load and replica read load.
  • Define which reads require the primary or a caught-up replica.
  • Practice promotion and prove the old primary is fenced.
