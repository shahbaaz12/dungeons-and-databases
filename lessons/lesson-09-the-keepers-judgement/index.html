01 · Start with what ran out

"The database is slow" is not a diagnosis.

Every technique in this course fixes exactly one kind of exhaustion. Applying the wrong one is how teams spend six months sharding a database that needed an index — and end up with both the original problem and a permanent new one.

So the first question is never which tool. It is which resource has run out.

Triage
The symptom What has actually run out Where to look first
Reads slow, buffer hit ratio low Memory — the working set does not fit An index, to touch fewer pages. Then partitioning, to shrink the hot slice
Reads slow, hit ratio high CPU, or the shape of the query The query itself. The storage layer is not your problem
Writes slow, commits queuing Write throughput — one log, one disk Drop unused indexes. Then a bigger machine. Then shard
Disk filling up Storage Partitioning plus a retention policy. Then shard
Read volume beyond one machine Read capacity Replicas
Downtime when a machine dies Availability Replication and a tested failover
Someone deleted the wrong rows History Backups. Replicas cannot help you here

Notice how many rows do not lead to sharding. That is the point of the table.

02 · The order of work

You did not learn them in the order you should apply them.

This course taught sharding before replication, because sharding follows naturally from partitioning — both are about splitting data. That was a teaching decision.

In practice the order is different, because what matters when choosing is not how similar two tools are. It is how much each one costs you if you are wrong.

Cost of being wrong
Tool Reversible? Changes application code?
Index Yes — DROP INDEX, instantly No
Partition Hard — the key means rewriting the table No, but queries must carry the key
Replica Yes — remove it and nothing breaks Yes — you must decide which reads tolerate staleness
Shard Effectively no Yes — routing, joins, transactions, IDs, everything after

So the ladder, cheapest and most reversible first:

  • Measure. Find the constraint before touching anything.
  • Fix the query, and add the index it deserves. Most "we need to scale" conversations should end here.
  • Remove the indexes nobody uses, so writes stop paying for maps no query reads.
  • Partition, if the data has a natural boundary your queries already use and history needs expiring.
  • Buy a bigger machine. Badly underrated. It costs less than the engineering months the next two steps consume.
  • Add replicas for read capacity and for surviving a failure.
  • Shard — only when writes are what ran out.

Replication moves ahead of sharding here, even though you met it later. It is reversible, it solves the more common problems, and it is the only one of the two that addresses a machine dying rather than a machine being full.

03 · What each tool buys

Nothing here is free. Know what you are paying.

The complete ledger
Tool Buys you Charges you
Index Far fewer pages per query Slower writes, storage, competition for buffer slots
Partitioning Less data per operation; instant retention; bounded maintenance A near-permanent key, multiplied indexes, planning overhead
Replication Read capacity and survival Lag, and a choice between losing data or losing availability
Sharding Write throughput — the only thing that raises it Fan-out, lost joins, lost transactions, routing, rebalancing
Backups The ability to undo yourself Storage, and a restore time measured in hours

Read the last two rows together. Replication and backups look like the same idea and solve opposite problems — one protects you from a machine, the other from your own mistakes. Neither substitutes for the other.

04 · The rule that never changed

The structure only helps queries shaped like it.

One rule appeared at every scale in this course, wearing a different name each time:

  • An index only helps queries that match its leading column.
  • A partition only prunes if the query filters on the partition key.
  • A shard can only be targeted if the query carries the shard key.

Same principle, three scales — and the penalty for breaking it grows each time. Miss the leading column and you read some extra pages. Miss the partition key and you open every partition. Miss the shard key and you send a request to every machine you own.

Which gives one practical instruction that outranks the rest: choose keys from the queries you actually run, never from what looks tidy in the schema.

05 · How this goes wrong

Seven mistakes, each one a tool aimed at the wrong problem.

  • Sharding a read problem. Enormously expensive, permanent, and an index or a partition would have done it. Ask what ran out first.
  • Adding indexes to fix slow writes. Every index makes writes slower. This is the one mistake that actively deepens the problem it was meant to solve.
  • Adding replicas to fix write throughput. Every write still passes through the one primary, and now gets shipped and replayed as well. Replicas make writes marginally worse.
  • Treating replicas as backups. A replica reproduces your DROP TABLE faithfully, in milliseconds. It has no memory of last Tuesday.
  • Hash partitioning, then wanting range queries. Hashing spreads rows evenly and destroys pruning. If you wanted to skip work rather than balance it, you chose the wrong strategy.
  • Rewriting SQL when the pages are not in memory. No phrasing of a query defeats physics. If the hit ratio is low, the data is on disk, and only fewer pages or more memory helps.
  • Reaching for anything before measuring. Every mistake above begins here.

06 · The judgement

Choose the smallest thing that solves the measured limit.

That sentence is the whole lesson. Every word in it is load-bearing.

Smallest, because complexity is permanent and capacity is cheap. Solves, because a technique that does not address the actual constraint is not a partial fix, it is a new problem laid on top of the old one. Measured, because without evidence you are choosing by instinct — and instinct reaches for whatever you read about most recently.

The three questions worth asking out loud before any of it:

  • What ran out? Name the resource, with a number attached.
  • What is the cheapest thing that would fix it? Start at the top of the ladder, not the bottom.
  • What will this cost me forever? Some doors do not open again.

You will not always get this right. But a keeper who can say which resource ran out, and why this tool addresses it, is already doing something most never do — and can defend the answer when someone asks.
