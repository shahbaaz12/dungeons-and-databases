Lesson 07 · Beyond one keep

Split the data. Inherit the map.

Sharding places different rows on different database machines. It is the first tool in this journey that creates independent write paths—and the first that makes routing part of every query.

Shard keysRoutingFan-outRebalancing

The Dragon’s Counsel

“More vaults mean more foundations—and a map for every key.”

The write ceiling rises because responsibility moves into the application.

01 · The real split

Each shard owns different data and different resources.

A replica copies the whole database. A partition divides a table but remains on one instance. A shard places one part of the data on one database machine and another part elsewhere. Shard A and Shard B have separate CPUs, buffer pools, storage devices, WAL streams, and write locks.

Writes for different shards can now proceed on different machines. This is why sharding meaningfully raises the write ceiling. The cost is equally direct: the application must know where data lives, and operations that once relied on one database boundary may cross several independent systems.

02 · The irreversible question

Which value decides where every row lives?

The shard key is the input to the routing decision. A strong key has high cardinality, spreads load evenly, and appears naturally in common queries. Those goals often pull against each other.

01Many values

Enough distinct keys to divide the data into useful pieces.

02Even work

No single value should own most rows or most traffic.

03Known at query time

Requests should arrive with the key so they can reach one shard.

customer_id is often a good fit for a multi-tenant orders system because most operations already belong to one customer. A timestamp may appear in every query but send all new writes to the newest range. Random order IDs distribute well but make “all orders for this customer” a multi-shard request. A shard key is a query-design decision, not just a distribution formula.

There is no universal winner. Stable uniform tenants may fit consistent hashing. A SaaS product with a few enormous customers may need a directory so one tenant can be moved deliberately. The design must explain how routing information is cached, updated, recovered, and kept consistent during movement.

04 · What one database used to do

Queries without the key become distributed work.

If a request includes the shard key, the router can send it to one machine. If it asks for “the newest 100 orders in the whole system” without a key, every shard may need to search locally, return candidates, and let the application merge and sort them. That is scatter-gather.

Cross-shard joins no longer look like ordinary SQL joins. Teams typically avoid them by keeping related rows on the same shard, duplicating small reference data, denormalizing a read model, or joining results in application code. Cross-shard transactions require coordination such as two-phase commit, where one failed participant can leave resources locked while everyone waits for a decision.

Key presentOne route · one database

Local joins, local transactions, and predictable latency remain possible.

Key absentFan out · merge results

Cost and tail latency grow with the number of shards contacted.

Even IDs become architectural. Random UUIDv4 values avoid a central generator but scatter inserts through B-tree leaves. UUIDv7, ULID, and Snowflake-style identifiers keep time order while remaining globally unique enough for distributed creation.

05 · Balance is more than row count

One hot tenant can own an otherwise even shard.

A hash can spread keys evenly while traffic remains uneven. One enterprise tenant may generate more work than ten thousand small tenants. That tenant can saturate its shard while the others remain quiet. It may need a dedicated shard or a second-level split within the tenant.

Fan-out magnifies slow tails too. If each shard has a 99% chance of responding within the target, a request waiting for 100 shards has only 0.99¹⁰⁰ ≈ 36.6% chance that every shard stays within it. In other words, roughly 63% of those requests encounter at least one slow shard.

This is why a shard count is not merely a capacity number. Every added destination changes the cost of global queries, observability, backups, migrations, and incident response.

06 · Moving a live boundary

Rebalancing is a migration, not a copy command.

Eventually a shard grows too large or one tenant must move. Copying its old rows is only the beginning, because new writes continue during the copy. A safe migration usually establishes a period in which the old and new locations cannot silently diverge.

  1. 01
    Prepare and dual-write

    Create the destination and ensure new changes reach both locations or enter a replayable change stream.

  2. 02
    Backfill history

    Copy existing rows in bounded batches while ordinary traffic continues.

  3. 03
    Verify

    Compare counts, checksums, and recent writes until the destination is demonstrably complete.

  4. 04
    Cut over and clean up

    Change the route, watch errors and lag, then remove the old copy only after the rollback window closes.

07 · The final threshold

Shard only after the single-machine remedies earn their limits.

First fix the access path. Then consider caching repeated answers, replicas for read load, partitions for pruning and lifecycle, and a larger machine when it buys simple headroom. Sharding is justified when the measured limit is truly the write, storage, or working-set capacity of one database—and the application is ready to own routing and distributed operations.
