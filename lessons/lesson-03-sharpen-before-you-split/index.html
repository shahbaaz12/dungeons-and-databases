Lesson 03 · The cheaper answer

Touch fewer pages before adding machines.

The query asks for fifty orders. The database should not search a million pages to find them. Before we split the realm, we will give PostgreSQL a shorter path through the vault.

Access pathsB-tree indexesQuery plansWrite cost

The Dragon’s Counsel

“Before building more vaults, teach the scribe where to look.”

The cheapest page is the page the query never needs to touch.

01 · Begin with the page count

How many pages did the query touch?

Lesson 02 taught us that every required page must be present in RAM. Now we reduce the number of pages required in the first place.

The request Show one customer’s 50 newest orders. 
SELECT *
FROM orders
WHERE customer_id = 84217
ORDER BY created_at DESC
LIMIT 50;

Imagine that orders contains 10 million rows. At our simplified eight rows per page, the table occupies about 1.25 million pages. Returning only 50 rows does not make the query cheap if PostgreSQL must inspect most of those pages to locate them.

Without a useful index

Search the table

A sequential scan examines page after page and rejects rows belonging to other customers.

Potential journey · 1,250,000 table pages
With a useful index

Follow the guide

An index leads PostgreSQL to the matching entries, which then point to the required table rows.

Illustrative journey · about 53 pages

These counts are a teaching model. Real plans depend on row size, cached pages, data distribution, table statistics, clustering, and the columns the query returns.

02 · The ordered guide

An index is a smaller path to the rows.

Like the index at the back of a book, a database index stores ordered keys and directions to the full records. PostgreSQL’s default index type is a B-tree.

A B-tree starts with a small root page, narrows through branch pages, and reaches a leaf page containing matching index entries. The tree stays shallow, so a large index can often be navigated with only a few page visits.

For our query, the index should begin with customer_id, because that is the equality filter. Within each customer, created_at DESC keeps newest orders first. PostgreSQL can find the customer, read in the requested order, and stop after 50 entries. 

CREATE INDEX orders_customer_created_idx
ON orders (customer_id, created_at DESC);

One search path

Root pageWhich range?
↓
Branch pageCustomers 80k–90k
↓
Leaf pageCustomer 84217 · newest first
↓
Table pagesFetch the 50 rows

PostgreSQL notes that multicolumn B-tree indexes are most efficient when query constraints use their leading columns. See the official multicolumn-index documentation.

03 · Count the new journey

The index changes the page budget.

The index does not make pages free. It replaces a broad search with a short tree walk and a focused set of table-page visits.

Broad search 1,250,000 possible table pages examined
→
Guided search ≈53 3 index pages + up to 50 table pages

The “up to 50” assumption is deliberately cautious: it imagines every returned row living on a different table page. If nearby orders share pages, fewer table-page visits are needed. If a covering index can answer the query by itself, PostgreSQL may avoid table-page visits altogether.

The Old Dragon “Do not admire the speed first. Count the doors that no longer opened.”

04 · Ask PostgreSQL what happened

The query plan reveals the chosen path.

PostgreSQL’s planner compares possible paths and chooses the one it estimates will cost least. EXPLAIN lets us inspect that choice instead of guessing.

05 · Every shortcut has a price

An index saves reads by adding work elsewhere.

An index is another data structure that PostgreSQL must store and keep correct. It should earn its place through queries that matter.

ReadsUsually cheaper

Selective queries can reach a small part of the table instead of examining most of it.

WritesMore work

Inserts, deletes, and changes to indexed values must also update the index.

Storage and memoryMore space

Index pages consume disk space and compete with table pages for cache.

This is why “index every column” is not a strategy. Start with an important query, design an index that matches its filter and ordering, measure the page reduction, then decide whether the added write and storage cost is worth paying.

The Dragon Explains

“A good index is a bargain struck with a known query.”

If a query needs most of the table, walking an index and then visiting many table pages can cost more than a sequential scan. The planner may correctly ignore the index. The goal is not “use an index”; the goal is “touch the fewest useful pages at an acceptable total cost.”

The Dragon’s Reckoning

Where we stand

One justified index changed the route through the same database. We removed page work before considering a more complicated architecture.

What we learnedAn index is an access path

It trades a broad table search for a short ordered guide to matching rows.

What we solvedThe customer-history query

A matching composite index can cut the illustrative page journey from 1.25 million to about 53.

What remainsOld data still shares the table

Indexes help searches, but they do not create lifecycle boundaries for years of history.

Our system nowOne database · one justified index

Reads are sharper, writes cost a little more, and the architecture remains simple.
