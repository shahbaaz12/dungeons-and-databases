Lesson 03 · The cheaper answer

Touch fewer pages before adding machines.

The query asks for fifty orders. The database should not search a million pages to find them. Before we split the realm, we will give PostgreSQL a shorter path through the vault.

Access pathsB-tree indexesQuery plansWrite cost

The Dragon’s Counsel

“Before building more vaults, teach the scribe where to look.”

The cheapest page is the page the query never needs to touch.

01 · The question

How many pages must this query touch?

Lesson 02 ended with a rule: every page a query needs must occupy a slot in the buffer pool before a single row can be read. That rule is fixed. What we can still change is how many pages the query needs in the first place.

The request Show one customer’s 50 newest orders. 
SELECT *
FROM orders
WHERE customer_id = 84217
ORDER BY created_at DESC
LIMIT 50;

Suppose orders holds 10 million rows. Keeping lesson 02’s simplified model of about eight 1 KB rows per 8 KB page, the table occupies roughly 1.25 million pages:

Rows in the table10,000,000

10,000,000 rows ÷ 8 rows per page

8 KB table pages1,250,000

Here is the uncomfortable part. Nothing in that SQL tells PostgreSQL where customer 84217’s rows are. Without a guide, the only way to be certain it has found all of them is to examine every page and discard the rows belonging to everyone else. Returning 50 rows does not make a query cheap. The cost is the search, not the result.

So the question becomes practical: is there a structure that can tell PostgreSQL where those fifty rows live, without reading the table to find out?

02 · What an index stores

An index is small because it does not hold your rows.

An index entry stores only two things: the key it is sorted by, and a pointer to where the full row lives in the table. A row in our example is about 1 KB. An index entry on a couple of columns is closer to 30 bytes.

That size difference is the whole mechanism, because it decides how many entries fit on one 8 KB page. A table page holds about 8 rows. An index page holds roughly 250 entries. And that ratio compounds every time you stack another level.

PostgreSQL’s default index is a B-tree: a stack of sorted pages where each page tells you which page to read next. Work out how tall it must be to cover 10 million rows, at 250 entries per page:

The leaves hold one entry per row, so 10,000,000 ÷ 250 gives 40,000 leaf pages. One level up, 40,000 ÷ 250 gives 160 branch pages. One more level up, 160 entries fit comfortably on a single root page.

So the tree is three levels deep, and a lookup reads exactly three index pages: root, branch, leaf. Not because three is a tuned number, but because 250 × 250 × 250 is already more than 10 million.

One search path

Root pageWhich range?
↓
Branch pageCustomers 80k–90k
↓
Leaf pageCustomer 84217 · newest first
↓
Table pagesFetch the 50 rows

This also explains something lesson 02 left implicit. The root and branch levels together are only 161 pages — about 1.3 MB. Every single lookup passes through the root, so its clock-sweep score never falls to zero and it is never chosen for eviction. The top of the tree simply lives in RAM permanently.

The practical effect is that navigation becomes free. A lookup nominally costs three index page reads, but two of them are always buffer hits. Roughly a megabyte of RAM is what lets PostgreSQL find any row in a ten-gigabyte table.

03 · Column order

A multicolumn index is sorted in one direction only.

An index helps only if its sort order matches the question. To see why, think about a phone book sorted by last name, then first name.

Finding everyone named Smith is instant, because every Smith sits together in one block. Finding Smith, John is instant too — narrow to Smith, then scan to John. But finding everyone named John means reading the entire book, because the Johns are scattered from Adams to Zhang. Same book, same data. One question is instant and the other reads everything, purely because of which column it filters on.

The reason is that sorting is hierarchical. The second column is only sorted within groups that share the same first column. Remove the filter on the first column and those groups mean nothing.

Our query filters on customer_id with an equality test, then wants the newest orders first. So customer_id must lead, and created_at DESC follows: 

CREATE INDEX orders_customer_created_idx
ON orders (customer_id, created_at DESC);

Now the leaf entries for customer 84217 are contiguous and already in the requested order. PostgreSQL walks to the start of that customer’s block, reads fifty entries, and stops. The ORDER BY costs nothing, because the index was already sorted that way. Reverse the two columns and both benefits vanish: the customer’s rows would be scattered across the whole index.

The general rule follows from the same mechanism — equality columns first, range and ordering columns last. An index can jump straight to an exact value, but once it reaches a range it has to start walking, and nothing after that point can be used to seek.

PostgreSQL notes that multicolumn B-tree indexes are most efficient when query constraints use their leading columns. See the official multicolumn-index documentation.

04 · The new page budget

Count the pages that no longer had to be read.

The index does not make pages free. It replaces a broad search with a short tree walk followed by a focused set of table visits.

An illustrative page count for one customer-history query
Access path What it reads Pages touched
Broad search Every page of the table, rejecting other customers’ rows ≈ 1,250,000
Guided search 3 index pages, then up to 50 table pages holding the matching rows ≈ 53

That is roughly 23,000 times fewer pages for the same answer. Notice where the saving comes from: not from reading faster, but from never opening the other 1,249,947 pages.

The “up to 50” half of that figure is deliberately pessimistic — it assumes every returned row sits on a different table page. If a customer’s recent orders were inserted around the same time, they often share pages, and the count drops. In the other direction, a covering index that already contains every column the query selects can answer it from the leaves alone, and the table visits disappear entirely.

These counts are a teaching model. Real plans depend on row size, which pages are already cached, data distribution, table statistics, physical clustering, and the columns the query returns.

05 · Ask, do not assume

The query plan tells you which path was chosen.

Creating an index is a suggestion, not an instruction. PostgreSQL’s planner estimates the cost of each available path and picks the cheapest. EXPLAIN lets us read that decision instead of guessing at it. 

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE customer_id = 84217
ORDER BY created_at DESC
LIMIT 50;
Before the index 
Seq Scan on orders
  Filter: customer_id = 84217
  Rows Removed by Filter: many
  Buffers: shared hit=… read=…
After the index 
Index Scan using
  orders_customer_created_idx
  Index Cond: customer_id = 84217
  Buffers: shared hit=… read=…

Two lines carry most of the meaning. Seq Scan versus Index Scan is the access path — which of the two rows in the table above actually happened. And Rows Removed by Filter is the wasted work made visible: rows that were read from a page, examined, and thrown away. A large number there is the signature of a missing index.

The Buffers line needs no new vocabulary, because lesson 02 already supplied it. shared hit counts pages found waiting in the buffer pool; shared read counts pages that had to be fetched into it first. Adding BUFFERS is what turns this lesson’s page arithmetic from a model into a measurement.

ANALYZE actually runs the statement; use care with writes. PostgreSQL explains these fields in the official Using EXPLAIN guide.

06 · The price

Every index is paid for on the write path.

An index is a second copy of part of your data, and PostgreSQL must keep it correct. Insert an order and the row is written to a table page — then a new entry must also be placed in the correct sorted position in the index, which means reading and modifying an index page too. Delete or change an indexed value and the same work happens again. Three indexes on a table means three of these on every write.

There is a subtler cost that lesson 02 lets us see clearly. Index pages are not stored somewhere special — they are ordinary 8 KB pages, and they live in the same buffer pool, competing for the same slots as your table pages. Our 40,161-page index is about 320 MB. On a 1 GiB buffer pool with 131,072 slots, holding it entirely would consume roughly a third of them.

That is why index every column is not a strategy. An index nobody queries still gets written to on every insert, and its pages still push table pages out of memory. An unused index does not merely cost nothing — it actively evicts data you do need.

The same accounting explains why the planner sometimes ignores a perfectly good index. A sequential scan harvests about eight useful rows per page. An index scan into scattered rows may visit one page per row. So once a query matches a large share of the table, the guided path can touch more pages than the broad one — and the planner is right to refuse it. The goal was never to use an index. The goal is to touch the fewest pages.

The Old Dragon “Do not admire the speed first. Count the doors that no longer opened.”

The Dragon’s Reckoning

Where we stand

One justified index changed the route through the same database. We removed page work before considering a more complicated architecture.

What we learnedAn index is an access path

Small entries make a shallow tree, and a shallow tree turns a search into a handful of page reads.

What we solvedThe customer-history query

A composite index matching the filter and the ordering cut the illustrative journey from 1.25 million pages to about 53.

What remainsOld data still shares the table

Indexes shorten searches, but they do not create lifecycle boundaries for years of history.

Our system nowOne database · one justified index

Reads are sharper, writes cost a little more, and the architecture remains simple.
